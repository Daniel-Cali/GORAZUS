## 3. Módulos incompletos

  módulos que compone).
- **Base de datos** — modelo completo y aplicado, pero:
  - 🔴 **RLS no aísla nada contra el tráfico real de la API.** Confirmado sistémico (no solo

  - 🟡 Documentación de métricas de la BD (`DATABASE_STRUCTURE.md`) desactualizada frente al estado

- **CI/CD** — `pr-validation.yml` es real; `deploy-staging`, `deploy-production` y

## 6. Deuda técnica

- **Infraestructura de build monorepo**: los path aliases de `tsconfig.base.json` apuntan a `.ts`
  fuente entre paquetes en vez de a artefactos compilados — funciona con `ts-node`/Vite, rompe
  `@nx/js:tsc`. Solución real: TS Project References (`composite`+`references`) o restructurar el
  consumo hacia `.d.ts` ya compilados. Afecta a los 11 paquetes `core/*` y a todo `modules/*/backend`
  futuro.
- **Separación de roles de base de datos**: falta un rol de runtime sin ownership (o
  `FORCE ROW LEVEL SECURITY` en las ~501 tablas) para que RLS proteja de verdad.
- **`.dockerignore`** inexistente en todo el repo.
- **Migraciones**: script de bootstrap, no un framework de migraciones con historial/rollback.
- **185 FKs cross-schema**: decisión de negocio pendiente (¿se resuelven con eventos + IDs sueltos,
  o se acepta el acoplamiento?).

## 7. Prioridad de cada tarea (antes de seguir con más módulos de negocio)

1. 🔴 **Separar el rol de runtime de la BD del rol dueño** (o `FORCE ROW LEVEL SECURITY`) — sin esto,
   cada módulo nuevo hereda el mismo agujero de aislamiento multiempresa.
2. 🔴 **Agregar `.dockerignore`** — bloquea cualquier build de imagen realista, y por ende cualquier
   despliegue a staging.
3. 🟠 **Resolver `nx build`** (TS Project References) — necesario antes de que "producción" sea
   creíble; hoy solo funciona el modo dev vía `ts-node`.
4. 🟠 **Construir `seguridad` (Fase 1: roles/permisos)** — desbloquea `@RequirePermission` real en
   todo módulo siguiente (ya era el siguiente paso planeado).
5. 🟡 Decidir (ADR) qué hacer con los 185 FKs cross-schema antes de que crezcan más.
6. 🟡 Empezar a exigir tests junto con cada módulo nuevo (ya se corrigió la plomería de jest — no
   hay excusa técnica para seguir en ~2% de cobertura).

## 9. Recomendaciones para nivel Enterprise comparable a SAP B1/Odoo/Dynamics

1. No relajar Clean Architecture/DDD al acelerar módulos de negocio — el patrón ya validado en
   `auth` (entities con invariantes + repos puerto/adaptador + casos de uso) es el molde a repetir,
   no a simplificar por velocidad.
2. Cerrar el gap de RLS **antes** de sembrar datos reales de un cliente — es mucho más barato
   ahora que con datos de producción.
3. Tratar "test junto con el código" como no negociable a partir de acá — la plomería ya está
   arreglada, el único costo restante es escribirlos.
4. Priorizar el ADR de FKs cross-schema pronto — cuantos más módulos se construyan asumiendo el
   patrón actual, más caro será revertirlo si el ADR concluye que hay que hacerlo.
5. Mantener la disciplina de "Fase 1 (núcleo) / Fase 2 (avanzado)" por módulo que ya se usó en
   `auth` y se decidió para `productos` — es lo que permite llegar a un POS funcional en semanas,
   no meses, sin sacrificar arquitectura.
