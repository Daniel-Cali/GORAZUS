## 1. Visión

GORAZUS es un ERP empresarial modular para pequeñas y medianas empresas,
diseñado para competir en alcance funcional con SAP Business One, Odoo y
Microsoft Dynamics — pero con una base técnica moderna (React 19, NestJS,
PostgreSQL) y una arquitectura pensada para **crecer durante años**, no
para un MVP desechable.

Esto tiene consecuencias concretas de diseño:

- **Modularidad real, no cosmética.** Cada dominio de negocio (Ventas,
  Inventario, Contabilidad, etc.) es una unidad autocontenida con sus
  propias capas, sus propios tipos y su propio ciclo de vida. Un
  desarrollador debe poder trabajar en `ventas/` sin necesidad de
  entender `contabilidad/`.
- **Monolito modular, no microservicios prematuros.** Empezar con
  microservicios reales antes de conocer los límites de negocio es un
  error clásico (ver [Martin Fowler, MonolithFirst]). GORAZUS se
  construye como un monolito modular con fronteras tan estrictas que
  extraer un módulo a un servicio independiente el día de mañana sea un
  cambio de infraestructura, no una reescritura. Ver
  [10-evolucion-a-microservicios.md](./10-evolucion-a-microservicios.md).
- **Alcance por módulo, nunca por plantilla.** Ningún módulo hereda
  pantallas o capacidades "porque los demás las tienen". Cada pantalla,
  entidad o endpoint debe justificarse con una necesidad de negocio real
  de ese módulo específico. Ver
  [04-catalogo-modulos-negocio.md](./04-catalogo-modulos-negocio.md).
- **Lenguaje ubicuo en español.** Los nombres de dominio (`ventas`,
  `compras`, `inventario`...) se mantienen en español porque así los
  nombra el negocio — es el mismo vocabulario que usarán los usuarios
  finales, los analistas funcionales y la documentación contable/fiscal
  local. Los términos técnicos genéricos (`controller`, `service`,
  `repository`) se mantienen en inglés por ser estándar universal en la
  industria. Ver [07-convenciones-y-estandares.md](./07-convenciones-y-estandares.md).

## 2. Principios rectores

| Principio                           | Cómo se aplica en GORAZUS                                                                                                                                                                                    |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Clean Architecture / Hexagonal**  | Cada módulo backend separa dominio, aplicación, infraestructura e interfaz. Las dependencias siempre apuntan hacia adentro.                                                                                  |
| **SOLID**                           | Servicios con responsabilidad única, dependencias inyectadas por interfaz (repositorios como puertos), módulos abiertos a extensión vía eventos y cerrados a modificación de sus internos por otros módulos. |
| **DRY**                             | Código compartido vive en `core/`, `ui-kit/` o `packages/` — nunca se duplica lógica entre módulos. Pero DRY no es excusa para acoplar dos módulos que solo comparten forma, no significado.                 |
| **KISS**                            | No se introduce un patrón (CQRS, event sourcing, saga) hasta que la complejidad real del módulo lo justifique. Ver la nota de alcance en cada documento.                                                     |
| **Separación de responsabilidades** | Un controller nunca contiene lógica de negocio. Un repositorio nunca conoce reglas de negocio. Un componente de React nunca llama a Prisma.                                                                  |
| **Preparado para microservicios**   | Fronteras de módulo = futuras fronteras de servicio. Comunicación entre módulos ya modelada como si cruzara una red (contratos explícitos, eventos, sin transacciones distribuidas implícitas).              |
| **Alcance real, no simetría**       | Ver memoria de proyecto: nunca replicar mecánicamente pantallas/capacidades de un módulo a otro sin confirmar necesidad de negocio.                                                                          |

## 4. Glosario mínimo

- **Módulo**: unidad de negocio autocontenida (`ventas`, `inventario`, ...). Tiene su propia porción backend, frontend y contratos compartidos.
- **Core**: código de infraestructura transversal que no representa una capacidad de negocio (base de datos, cache, mensajería, seguridad técnica).
- **Shared Kernel**: el conjunto mínimo de tipos/contratos que **todos** los módulos pueden depender sin pedir permiso (`Money`, `TenantId`, `UserContext`). Deliberadamente pequeño.
- **Módulo dueño**: el único módulo autorizado a escribir el estado de una entidad. Otros módulos la consumen por ID o por proyección de solo lectura.
- **Evento de dominio**: hecho de negocio ya ocurrido e inmutable (`VentaConfirmada`), publicado para que otros módulos reaccionen sin acoplamiento directo.
- **Composition root**: el punto de entrada delgado (`apps/api`, `apps/web`) que ensambla módulos, pero no contiene lógica de negocio propia.
